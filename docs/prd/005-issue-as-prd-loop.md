# PRD 005: Issue-as-PRD Loop with Sub-task Readiness Gate

## Problem Statement

The backlog-clearer loop takes one already-triaged issue, forks a branch from the mainline, runs one bounded per-issue coder<->reviewer pipeline over the whole issue, and delivers a review-ready branch. That works only when an issue is already small enough to implement in one scoped diff. Larger triaged issues overwhelm the per-issue pipeline: the diff grows past the reviewable size limit, the reviewer cannot reason about the whole change, and the loop eventually marks the issue stuck instead of delivering anything.

A human faced with a large issue would decompose it into smaller pieces, implement each piece in turn, and only then review the whole thing. The PRD loop already accumulates pre-existing PRD issues on one branch and quality-gates the completed branch, but it does not perform the initial decomposition of a raw PRD. The backlog loop has no equivalent decomposition or post-implementation quality gate. It needs to treat a single large backlog issue the way the PRD loop treats a prepared PRD issue set: break it down, build the pieces up on one branch, and quality-gate the result once — all without human intervention or a parallel local state store. The generated GitHub issues remain as a durable audit trail.

Separately, decomposition alone is not enough. A freshly decomposed sub-task is often under-specified for the small coder model that will implement it: it may be missing acceptance criteria, may restate facts that are wrong against the repository, or may describe work that is already done. Handing such a sub-task straight to the coder wastes a full coder<->reviewer cycle. The loop needs to sharpen each sub-task against the original issue and the repository before any coder starts.

## Solution

Turn `run-backlog-v3` into the **Issue-as-PRD loop**: each triaged backlog issue becomes its own PRD for one pass. The loop decomposes the parent issue into sub-task child issues, sharpens each sub-task with a readiness gate, drains the sub-tasks onto a per-issue accumulation branch through the normal coder<->reviewer engine, runs exactly one extra review round, drains any follow-ups once, and then delivers the accumulation branch review-ready. The outer backlog loop is preserved: after one parent finishes, the loop advances to the next eligible backlog issue.

The incoming issue plays the PRD role. Sub-tasks are tracked as true GitHub child issues under the parent and also carry a per-parent label. The child relationship provides tracker hierarchy and auditability; the label remains the authoritative queue selector so the loop can reuse the existing publication, duplicate-detection, queue-decision, and bounded extra-review patterns instead of inventing a parallel state store. Sub-task branches fork sequentially from the accumulation branch so each sub-task sees previously-integrated work and then integrates back into it. The single extra review round reuses the existing bounded extra-review orchestration, capped at one round, so a completed parent is quality-gated exactly once before delivery.

Between each decomposition and its drain, a **sub-task readiness gate** runs once over every newly created sub-task, including both initial children and extra-review follow-ups. It reuses the reviewer model but has its own agent and prompts, runs in a clean context per sub-task, and receives that sub-task, the parent issue as PRD, the current sibling-batch list, and repository access. It blends triage-style actionability classification with issue-readiness completeness and accuracy checks, then emits a complete proposed replacement body and a machine-readable disposition. The host validates that output, applies and verifies any GitHub issue edit, and decides proceed-versus-drop. The gate never marks a sub-task stuck by itself.

Direct-parent work, child-issue work, and the PRD loop must not retain separate copies of the coder<->reviewer pipeline. That pipeline is extracted behind one shared per-branch engine used by `run-backlog-v3.mts` and `run-prd-v4.mts`. No older backlog or PRD runner is changed.

## User Stories

1. As a loop operator, I want a large triaged backlog issue to be decomposed into smaller sub-tasks, so that the loop can deliver work that a single coder pass could not.
2. As a loop operator, I want the incoming issue to act as the PRD for its sub-tasks, so that decomposition and review are grounded in the original intent without a separate PRD file.
3. As a loop operator, I want each parent issue processed as its own mini-PRD, so that decomposition, drain, review, and delivery are scoped to one issue at a time.
4. As a loop operator, I want the outer backlog loop preserved, so that the loop keeps clearing the labeled backlog one parent issue at a time.
5. As a loop operator, I want the loop to reuse the existing issue-decomposer model and role, so that decomposition quality matches the rest of the system.
6. As a loop operator, I want the initial decomposition to use its own prompts fed the normalized parent context and repo context, so that it works without the review artifacts the existing decomposer prompt assumes.
7. As a loop operator, I want sub-tasks tracked as GitHub child issues, so that the existing queue, publication, duplicate-detection, and drain machinery can be reused.
8. As a loop operator, I want each child issue to carry a per-parent label, so that the inner drain can select a parent's sub-tasks without colliding with the outer backlog queue.
9. As a loop operator, I want child issues created with a stable duplicate marker, so that re-running a parent does not create repeated sub-task tickets.
10. As a loop operator, I want a parent claim to be durable, idempotent, and resumable after a process crash, so that the outer loop neither works the same parent concurrently nor strands it outside the queue.
11. As a loop operator, I want the accumulation branch forked fresh from the mainline for each parent, so that a parent's work does not build on unrelated in-progress branches.
12. As a loop operator, I want each sub-task branch forked from the accumulation branch tip, so that later sub-tasks build on previously-integrated sub-task work.
13. As a loop operator, I want each completed sub-task branch fast-forwarded into the accumulation branch and checkpointed to origin, so that the parent's implementation accumulates durably in one place without temporary pull requests.
14. As a loop operator, I want a sub-task's reviewer to compare the sub-task branch against the accumulation branch tip, so that review is scoped to that sub-task's changes.
15. As a loop operator, I want a completed sub-task's child issue closed, so that the tracker reflects which sub-tasks are done and the inner queue drains.
16. As a loop operator, I want sub-tasks drained sequentially, so that interdependent decomposed work is implemented in a coherent order.
17. As a loop operator, I want a parent with zero decomposition drafts worked directly as a single coder<->reviewer task, while every generated draft is persisted and readiness-gated as a child issue, so that useful decomposition output is never discarded or held only in process memory.
18. As a loop operator, I want a directly-worked small parent to still receive the single extra review round, so that every delivered parent gets the same quality gate.
19. As a loop operator, I want exactly one extra review round after the sub-tasks drain, so that a completed parent is quality-gated without an unbounded review cycle.
20. As a loop operator, I want the single extra review round to compare the accumulation branch against its recorded full-parent review base, while retaining the original fork SHA and any failed refresh attempt as provenance, so that reviewers inspect only the parent implementation regardless of whether the pre-review mainline refresh succeeded or was aborted.
21. As a loop operator, I want extra-review follow-ups created as child issues under the same parent label, so that they drain through the same inner queue.
22. As a loop operator, I want the extra-review follow-ups drained exactly once, so that the loop finishes a parent after one review-and-fix pass rather than re-reviewing indefinitely.
23. As a loop operator, I want no second extra review round after the follow-ups drain, so that the loop stops for the parent as configured.
24. As a loop operator, I want a finished parent delivered review-ready by pushing the accumulation branch and labeling the parent for review, so that a human opens the pull request.
25. As a loop operator, I want the loop to never auto-merge or auto-close a parent, so that delivery matches the backlog loop's review-ready contract.
26. As a loop operator, I want a stuck sub-task to halt the initial drain, quality-gate whatever has already integrated, and deliver that reviewed partial work, so that partial progress is neither thrown away nor exempted from the parent-level review contract.
27. As a loop operator, I want a partially-delivered parent marked with `Review` plus `agent-partial`, while the failed child retains `agent-stuck`, so that a human can distinguish usable incomplete delivery from a parent-level failure that produced nothing reviewable.
28. As a loop operator, I want the loop to advance to the next backlog issue after a partial delivery, so that one hard parent does not wedge the backlog.
29. As a sub-task implementer, I want each sub-task sharpened before I start, so that I receive a self-contained, accurate specification.
30. As a loop operator, I want a readiness gate to run over every initial or extra-review-generated sub-task after its decomposition and before any coder, so that no coder starts on an under-specified sub-task.
31. As a loop operator, I want the readiness gate to reuse the reviewer model with its own agent and prompts, so that gate behavior is tuned independently from code review.
32. As a loop operator, I want the readiness gate to run in a clean context per sub-task, so that one sub-task's review does not bias another's.
33. As a loop operator, I want the readiness gate to receive the sub-task, normalized parent context as PRD, the active sibling-batch list, and repo access, so that it can check completeness, accuracy, dependencies, and overlap.
34. As a loop operator, I want the readiness gate to blend actionability classification with completeness and accuracy checks, so that it catches both dead work and under-specification.
35. As a loop operator, I want the readiness gate to return a corrected full issue body for the host to validate, apply, and verify, so that the coder reads a corrected specification and tracker mutation remains host-owned.
36. As a loop operator, I want a sub-task the gate cannot make workable to still proceed with an explicit recommended-default assumption recorded in its body, so that the autonomous loop never blocks on a human answer.
37. As a loop operator, I want the gate to close and drop a sub-task that is a duplicate or already implemented, so that the loop does not code work that has no effect.
38. As a loop operator, I want a dropped sub-task removed from the inner drain queue without a branch, so that pruned work never reaches a coder.
39. As a loop operator, I want readiness invocation, parsing, and tracker-update failures to have an explicit deterministic host disposition and never silently corrupt queue state.
40. As a loop operator, I want every gate outcome emitted as machine-readable tagged output, so that the host can decide proceed-versus-drop without scraping prose.
41. As a maintainer, I want the coder<->reviewer per-branch engine extracted into one shared module used by `run-backlog-v3.mts` and `run-prd-v4.mts`, so that direct-parent, child-issue, and PRD-issue execution cannot drift structurally.
42. As a maintainer, I want the shared per-branch engine covered by tests at its module seam, so that both runners inherit the same verified mechanism while retaining explicit policy differences.
43. As a loop operator, I want decomposition, gate, and delivery vocabulary recorded in the domain glossary, so that the team shares one language for the new loop.

## Implementation Decisions

- The Issue-as-PRD loop keeps the outer backlog queue. Before selecting fresh work, it first looks for the lowest-numbered open parent carrying all configured backlog labels plus `agent-in-progress` and resumes that parent. Only when no matching in-progress parent exists does it select the lowest-numbered fresh eligible parent.
- A parent retains its configured backlog labels throughout its lifecycle. Claiming adds `agent-in-progress`; fresh-parent selection excludes that label, while the resume pass requires it. Claim and resume operations are idempotent and reconstruct progress from the stable accumulation branch, child issues, their labels, and the parent's tagged state comment rather than from process memory.
- Clean delivery removes `agent-in-progress` and adds `Review`. Partial delivery removes `agent-in-progress` and adds `Review` plus `agent-partial`; it does not add `agent-stuck` to the parent, while the child that caused the halt retains `agent-stuck`. An unrecoverable parent-level failure that produced no reviewable delivery removes `agent-in-progress` and adds parent-level `agent-stuck` without `Review`. Existing terminal-label exclusions continue to prevent delivered or failed parents from re-entering the fresh queue even though their backlog labels remain.
- Claims do not expire automatically. An operator must explicitly clear or repair `agent-in-progress` when intentionally abandoning a parent whose durable branch and issue state cannot be resumed.
- Each parent has exactly one host-managed GitHub state comment containing a unique `sandcastle-issue-as-prd-state` marker and a schema-versioned tagged JSON block. At minimum it records the parent number, accumulation branch, original fork-point SHA, current full-parent review-base SHA, latest mainline SHA observed at delivery, current phase, per-parent label, completed extra-review rounds, aggregate-validation repair budgets by gate, and last durable transition timestamp. The host creates or updates this comment idempotently after each durable transition; labels, branches, and child states remain independently verifiable so recovery can detect rather than conceal disagreement.
- The state comment is orchestration metadata, not product intent. Parent-comment normalization excludes any comment carrying the state marker before applying the human-comment byte cap, so decomposition, readiness, coding, and review agents never receive it as requirement context.
- Unless a narrower budget is specified, host-side GitHub mutations use up to three idempotent attempts followed by read-back verification. On exhaustion, the host preserves local/remote branch state and diagnostics and attempts the parent-level `agent-stuck` transition. If even the terminal label transition cannot be verified, the runner stops with an operator handoff rather than continuing with ambiguous ownership or queue state.
- Sub-tasks are true GitHub child issues linked under the parent. Each child also carries a per-parent label derived from the parent number. The relationship is the tracker hierarchy; open issues carrying the per-parent label are the authoritative inner queue, so queue reconstruction does not depend on traversing the relationship API.
- Fixed labels are ensured idempotently: `agent-in-progress` uses color `fbca04` and description "Issue-as-PRD parent currently owned by the agent loop"; `agent-partial` uses color `d93f0b` and description "Review-ready branch contains a partial parent implementation"; `agent-rebase-needed` uses color `d4c5f9` and description "Review-ready branch needs a manual rebase onto current mainline". Each dynamic `parent-<N>` label uses color `1d76db` and description "Temporary Issue-as-PRD queue for parent #N".
- The dynamic `parent-<N>` label is retained while the parent is `agent-in-progress` or parent-level `agent-stuck`, because it remains part of recovery state. After clean or partial delivery, the host deletes that label only after the final branch push, parent terminal-label transition, and child-state verification have succeeded. The true child relationship preserves hierarchy, and future rerun deduplication searches linked children by marker rather than depending on a deleted label. Dynamic-label deletion failure is warning-only and does not roll back delivery.
- On first claim, the accumulation branch for a parent is forked fresh from the remote-tracking mainline, its fork-point SHA is recorded in the parent's durable loop-state marker, and the initial branch is pushed to origin as a recovery checkpoint. A resumed parent reuses and verifies this stable local/remote branch rather than forking again. The branch is the fast-forward target for sub-task branches and the branch ultimately delivered for review.
- The initial decomposition reuses the configured issue-decomposer model and role but has its own prompts. Its inputs are the parent issue body as the primary specification, normalized parent comments as supplemental context, and repository context. It does not receive code-quality or two-axis review artifacts, because none exist at decomposition time.
- Parent comments preserve author, timestamp, and chronological order. The body remains authoritative when it is merely supplemented; a substantive conflict is resolved through an explicit recorded assumption rather than silently overriding the body. A deterministic configured byte cap keeps the newest complete comments that fit, renders those retained comments chronologically, and inserts a visible truncation notice when older comments are omitted. The same normalized parent context is supplied to initial decomposition, each readiness run, direct-parent coding, and the full-parent extra review.
- Initial decomposition has an acquisition budget of two clean-context attempts. Each attempt uses the strict tagged contract and completion signal, and the host preserves raw output plus parser diagnostics. A valid result from either attempt is accepted; `needs_human_review`, incomplete output, malformed output, or invocation failure triggers the remaining attempt before becoming terminal.
- Exhausting both initial-decomposition attempts is an exceptional parent-level failure, not a direct-coder fallback. The host records the diagnostics on the parent, removes `agent-in-progress`, adds `agent-stuck`, and advances the outer queue. A valid `no_work` or zero-draft decomposition is not an acquisition failure and continues through the direct-parent fallback.
- The initial decomposition emits sub-task drafts as strict tagged output that the host parses and publishes as sub-task issues. The host, not the agent, creates each issue, ensures and applies the per-parent label, establishes the GitHub parent/child relationship idempotently, and writes a duplicate marker into the issue body. Publication is not complete until both the labeled issue and its relationship are verified; a created-but-unlinked issue is retried or surfaced through the parent-level publication failure path and is not eligible for draining.
- Duplicate prevention for child issues reuses the existing marker-and-search approach: before creating a child issue, the host searches open and closed issues for the same marker and skips creation on a match.
- If a valid initial decomposition yields zero drafts, the loop falls back to working the original parent directly as a single coder<->reviewer task on the accumulation branch, then still runs the single extra review round. If it yields one or more drafts, every draft is published as a durable child issue and passes through readiness before coding; a sole draft never exists only in memory and is never discarded in favor of the original body.
- Each sub-task branch forks from the accumulation branch tip, so later sub-tasks build on previously-integrated sub-task work. The sub-task reviewer compares the sub-task branch against that exact accumulation tip and records the reviewed base SHA with the engine outcome.
- Approved sub-task integration is a host-side fast-forward, not a pull request or merge commit. Before integration, the host verifies that the accumulation tip still equals the reviewer's base SHA and that the approved child HEAD descends from it. It then fast-forwards the accumulation branch to the approved HEAD, pushes and verifies the remote checkpoint, and only then closes the child issue. Sub-tasks are drained sequentially.
- Integration recovery is idempotent: if the local or remote accumulation branch already contains the approved child HEAD, the host completes any missing push, verification, or child-close step without creating another commit. A child issue is never closed before the remote accumulation checkpoint is verified.
- After the initial child queue drains and before full-parent validation or extra review, the host fetches the latest remote-tracking mainline. If mainline advanced beyond the original fork point, it preserves the current accumulation tip on a diagnostic checkpoint, rebases the accumulation branch once onto the fetched mainline, and replaces the remote accumulation checkpoint with force-with-lease protection. It then records the fetched mainline SHA as the full-parent review base while retaining the original fork SHA for provenance. If mainline has not advanced, the original fork SHA remains the review base and no history is rewritten.
- The one-time refreshed accumulation branch is the base for validation, the single extra-review round, and all follow-up child branches. The extra reviewers compare `full_parent_review_base_sha..accumulation_head`, not `original_fork_sha..accumulation_head`, so unrelated mainline changes are excluded from review.
- If the one-time rebase conflicts, the host aborts it, restores and verifies the unchanged pre-rebase accumulation checkpoint, and does not mark the parent stuck. It records the attempted mainline SHA and conflict diagnostics in the parent state and review artifacts, leaves the existing branch base as `full_parent_review_base_sha`, and continues with validation, the single extra-review round, and follow-up fixes against that unchanged base. The loop does not attempt a second automatic rebase after review; resolving the recorded mainline conflict is left to the human delivery workflow.
- Aggregate validation runs after the pre-review refresh and again after the one-time follow-up drain before terminal delivery. If either aggregate gate fails, the host may create at most one validation-repair child for that gate. Its body records the gate name, exact failing command and output, accumulation SHA, and acceptance criterion that the complete configured validation gate passes. It is linked under the parent, labeled with `parent-<N>`, readiness-gated, run through the shared engine, integrated by the normal fast-forward path, and followed by a complete aggregate-validation rerun.
- A successful pre-review validation repair is included in the full-parent extra review. A successful pre-delivery repair is covered by its child-level reviewer and the final aggregate rerun; it does not trigger a second full-parent review round, matching the one-time follow-up policy. If the repair child gets stuck or the aggregate gate remains red after its one repair budget, the host preserves the branch and diagnostics, removes `agent-in-progress`, marks the parent `agent-stuck` without `Review` or `agent-partial`, retains `parent-<N>` for recovery, and advances the outer queue.
- The sub-task drain reuses extracted per-branch engine behavior plus new per-parent queue and transition modules; the current normal-issue worker is inline and is not treated as an already-parameterized reusable module. The single extra review round reuses the existing bounded extra-review orchestration, parameterized by the per-parent label and a maximum of one round.
- The single extra review round compares the accumulation branch against the recorded full-parent review-base SHA, runs the existing independent review sessions and issue decomposer, and creates any follow-ups as child issues under the same per-parent label. The original fork SHA remains artifact provenance only after a refresh.
- Each full-parent review session has an acquisition budget of two clean-context attempts. Invocation failure, incomplete or malformed tagged output, an inconsistent contract, or `needs_human_review` consumes the remaining attempt without counting as another extra-review round. Raw output, parser diagnostics, and attempt metadata are preserved.
- If any required full-parent review session still lacks a trustworthy result after both attempts, the host pushes and preserves the implemented accumulation branch and review artifacts, removes `agent-in-progress`, adds parent-level `agent-stuck` without `Review`, retains the dynamic per-parent label for recovery, and advances the outer queue. No follow-up issues are published from an untrustworthy review result.
- Follow-ups from the single extra review round pass through the same readiness contract and failure budgets, then drain exactly once through the same inner drain. After they drain, no further extra review round runs. The Issue-as-PRD adapter treats the expected one-round budget exhaustion after a clean follow-up drain as successful completion and proceeds to parent delivery rather than exposing the PRD loop's `max_extra_review_rounds` handoff as an error.
- Terminal delivery fetches mainline once more, records the observed SHA, verifies and pushes the final accumulation tip, then labels the parent for review. Earlier checkpoint pushes do not make the parent review-ready; the terminal labels remain the delivery signal. If the pre-review mainline rebase conflicted and was aborted, or if the observed terminal mainline SHA differs from the recorded full-parent review base, delivery preserves the reviewed branch unchanged and adds `Review` plus `agent-rebase-needed`; otherwise clean delivery adds only `Review`. The loop never performs a second automatic rebase or full-parent review, and never auto-merges or auto-closes a parent.
- If an initial sub-task gets stuck through the normal stuck-detection paths, the initial drain halts and the failed child retains `agent-stuck`. If the accumulation branch contains integrated parent work, the adapter enters partial-review mode: the already-stuck child is excluded from the review-start queue gate, the partial accumulated diff receives the normal full-parent validation and single extra-review round, and any non-stuck review follow-ups are processed once before delivery. Successful partial delivery pushes the final reviewed tip and labels the parent with `Review` plus `agent-partial`.
- If the first failing child leaves the accumulation branch identical to its full-parent review base, there is no partial implementation to deliver. The host removes `agent-in-progress`, marks the parent `agent-stuck` without `Review` or `agent-partial`, retains the per-parent label and diagnostics for recovery, and advances the outer queue.
- A stuck review follow-up halts the one-time follow-up drain and delivers the already-reviewed-and-improved branch as `Review` plus `agent-partial`; no second extra-review round runs. A full-parent review acquisition failure still follows Decision 14 and marks the parent `agent-stuck` without `Review` because the partial branch never completed its quality gate.
- The sub-task readiness gate runs in two possible batches: once over all initial children after initial decomposition, and once over any extra-review follow-up children before the one-time follow-up drain. Each sub-task is gated exactly once before its first coder attempt. The initial batch grounds against the freshly forked accumulation branch; the follow-up batch grounds against the post-review accumulation tip and receives the follow-up sibling list.
- The readiness gate reuses the reviewer model but is its own custom agent with its own system and user prompts. It runs in a clean context per sub-task.
- The gate receives, per sub-task: that sub-task's body, the normalized parent context as PRD, the sibling sub-task list for dependency and overlap awareness, and repository access.
- The gate logic blends triage-style actionability classification with issue-readiness completeness and accuracy checks. The agent emits a strict tagged result containing its disposition, evidence, and a complete proposed issue body; it does not call GitHub or mutate the tracker.
- The gate assigns each sub-task one of three successful outcomes: fixed (findings resolved in the proposed body, proceed to coder), not-actionable (duplicate or already implemented, so the host closes and drops the issue with no branch), or assumed (unresolvable blocking ambiguity, for which the proposed body records an explicit recommended-default assumption and proceeds).
- Readiness-result acquisition has a budget of two clean-context agent attempts. A valid result from either attempt is accepted; invocation failure, incomplete output, malformed output, or an inconsistent contract consumes the remaining attempt. Raw output and parser diagnostics from both attempts are preserved.
- The host accepts only a valid, internally consistent gate result. For fixed and assumed outcomes, it applies the proposed body with `gh`, reads the issue back, and proceeds only after the persisted body matches. For not-actionable, it closes the issue and verifies that it has left the open inner queue. A valid result is not regenerated merely because its host-side mutation fails; that same idempotent mutation and read-back verification is attempted up to three times.
- Exhausting either the two readiness acquisition attempts or the three host mutation/verification attempts is an exceptional parent-level technical failure. The host records diagnostics, removes `agent-in-progress`, adds `agent-stuck`, and advances the outer queue. It never sends the coder an original, partially updated, or unverified issue body. This is distinct from a successful `assumed` result, which resolves semantic ambiguity and proceeds.
- A dropped sub-task is distinct from a stuck sub-task, which was attempted and failed during the drain. The readiness gate never applies the normal coder-pipeline stuck classification itself.
- The shared engine's `already-satisfied` outcome is routed by task source. For an initial child, the host verifies that the child branch has no diff from its reviewed accumulation base, closes the child with the agent's evidence, and relies on the full-parent review as the backstop. For an extra-review follow-up, `already-satisfied` is treated as unresolved: the child receives `agent-stuck` and the parent follows partial delivery because no second full review can confirm the finding. For a validation-repair child, the host immediately reruns aggregate validation and closes the child only if the gate is green; a still-red gate exhausts that repair path and marks the parent stuck. For direct-parent work, `already-satisfied` produces no reviewable branch, so the parent becomes `agent-stuck` without `Review`.
- The coder<->reviewer per-branch engine — rounds, pre-coder rebase guard, branch preparation and recovery, review-context computation, validation gate, reviewer-attempt acquisition, no-progress detection, and stuck classification — is extracted into one shared module called by the direct-parent and child-issue paths in `run-backlog-v3.mts` and the normal PRD-issue path in `run-prd-v4.mts`. It returns an exhaustive typed outcome such as approved, already-satisfied, stuck, or crashed; it does not integrate branches, close issues, deliver parents, or mutate queue labels.
- The shared engine accepts explicit policy inputs for the runner behaviors that already differ, including round budgets, no-progress thresholds, reviewer acquisition, base-ref resolution, and branch preparation. Characterization tests lock both runners' current behavior before extraction; the extracted mechanism preserves those explicit policies rather than silently forcing one runner's choices onto the other.
- Runner adapters own integration and tracker side effects. The PRD-v4 adapter preserves its existing merge-and-close contract. The Issue-as-PRD adapter uses the typed outcome to fast-forward a child, deliver a clean or partial parent, or apply the parent-level failure policy.
- The initial decomposer and readiness gate get explicit `initialIssueDecomposer` and `subtaskReadiness` model entries in `sandcastle-loop-config.mts`. Both default to the configured reviewer model when omitted and can be overridden independently, with config tests covering defaults and overrides.
- The maximum extra review round count for the Issue-as-PRD loop is a configuration constant whose value is one, kept adjustable rather than hardcoded into control flow.
- The Issue-as-PRD runner preserves the Companion TUI contract from ADR 0002 and ADR 0003. It emits `loopType: "backlog"`; uses `normal_issue` for claim, decomposition, readiness, initial/repair/follow-up drains, and delivery; and uses `extra_review` only for the full-parent review sessions and publication. Every new agent run goes through `recordMeasuredAgentRun` with a distinct stage name and working log; decomposition publication, label transitions, readiness result application, sub-task integration, full-parent review, and partial, rebase-needed, or clean delivery emit explicit host-step transitions. The status ticket identifies the active child during child work and the parent during parent-level host/review steps.

## Design Decisions

1. **Resolved — Parent claim and crash recovery:** the parent retains its backlog labels, gains `agent-in-progress` while owned, and is resumed before fresh work. Claims have no automatic expiry; explicit operator action is required to abandon one.
2. **Resolved — Sub-task tracker identity:** every sub-task is a true GitHub child issue. The `parent-<N>` label remains the authoritative queue selector, while the verified parent/child relationship supplies hierarchy and auditability.
3. **Resolved — Sub-task integration mechanism:** the host performs a compare-and-swap-style fast-forward from the reviewed accumulation base to the approved child HEAD, verifies a remote checkpoint, and then closes the child. It creates no temporary pull request or merge commit.
4. **Resolved — Initial-decomposition failure:** the host makes at most two clean-context acquisition attempts. If neither produces a valid actionable contract, the host records diagnostics, removes `agent-in-progress`, marks the parent `agent-stuck`, and advances the outer queue. Valid `no_work` or zero-draft output still takes the direct-parent path. This is an exceptional safety valve, not an expected control-flow path.
5. **Resolved — Readiness failure:** result acquisition gets two clean-context attempts; a valid result's idempotent host mutation and read-back verification get three attempts. Exhaustion records diagnostics, marks the parent `agent-stuck`, and advances the outer queue. The coder never receives an original or unverified body. A successful `assumed` result remains the non-terminal path for semantic ambiguity.
6. **Resolved — Decomposition fallback threshold:** only a valid zero-draft result works the original parent directly. One or more drafts enter the durable child-issue and readiness pipeline, including a sole draft.
7. **Resolved — PRD-runner scope:** exactly `run-backlog-v3.mts` and `run-prd-v4.mts` adopt the shared engine. All older runner variants remain unchanged.
8. **Resolved — Parent input:** the body is the primary specification and normalized comments are capped supplemental context for decomposition, readiness, direct-parent coding, and full-parent review. Retained comments keep metadata and chronological order; conflicts become explicit assumptions rather than silent overrides.
9a. **Resolved — Partial versus stuck labels:** a partially delivered parent receives `Review` plus `agent-partial` and never parent-level `agent-stuck`; the child that halted the drain retains `agent-stuck`. Parent-level `agent-stuck` without `Review` is reserved for failures that produce no reviewable delivery.
9b. **Resolved — Per-parent label retention:** retain `parent-<N>` for in-progress or parent-level stuck recovery, then delete it last after clean or partial delivery. Relationship-based marker search supports future deduplication. Cleanup failure is warning-only.
9c. **Resolved — Label provisioning:** fixed and dynamic labels are ensured idempotently with the names, colors, and descriptions specified above. `agent-in-progress`, `agent-partial`, and `agent-rebase-needed` are permanent repository labels; `parent-<N>` is temporary per active or recoverable parent.
10. **Resolved — Durable parent phase state:** one host-managed, schema-versioned tagged JSON comment records the accumulation branch, original fork SHA, current full-parent review-base SHA, phase, queue label, review and aggregate-validation repair budgets, and transition time. It is updated idempotently and excluded from all agent-facing parent-comment context.
11. **Resolved — Pre-review mainline refresh:** after the initial child drain, the host rebases the accumulation branch once onto the latest fetched mainline, checkpoints it with force-with-lease protection, and uses that mainline SHA as the full-parent validation/review base. The original fork SHA is retained only for provenance after a refresh.
12. **Resolved — Pre-review rebase conflict:** abort and verify the unchanged accumulation branch, record the attempted mainline SHA and conflict diagnostics, then continue validation, extra review, and follow-up fixes against the existing branch base. Do not mark the parent stuck and do not attempt another automatic rebase after review.
13. **Resolved — Rebase-needed delivery:** after an aborted pre-review rebase, successful terminal delivery adds `Review` plus `agent-rebase-needed`, preserving conflict diagnostics and the attempted mainline SHA for the human. It is neither `agent-partial` nor `agent-stuck`.
14. **Resolved — Full-parent review acquisition failure:** each required session gets two acquisition attempts within the one review round. Exhaustion preserves the branch and artifacts, removes `agent-in-progress`, marks the parent `agent-stuck` without `Review`, retains `parent-<N>` for recovery, and advances the outer queue.
15. **Resolved — Partial-delivery quality gate:** if at least one child integrated before another became stuck, the accumulated partial diff still receives full-parent validation, one extra-review round, and one follow-up drain before `Review` + `agent-partial` delivery. The original stuck child does not block review start. An empty partial branch becomes parent-level `agent-stuck`; a stuck review follow-up delivers the reviewed work as partial without another review round.
16. **Resolved — Follow-up readiness:** every extra-review-generated child receives the same one-time readiness gate, outcomes, acquisition budget, mutation verification, and failure policy as an initial child before the one-time follow-up drain.
17. **Resolved — Aggregate validation repair:** pre-review and pre-delivery aggregate gates each permit one host-generated validation-repair child carrying the exact failure evidence. The child is readiness-gated, reviewed, integrated, and followed by a complete validation rerun. Exhaustion marks the parent `agent-stuck` without a review-ready or partial delivery label.
18. **Resolved — Mainline movement after review starts:** terminal delivery fetches mainline but never rebases or re-runs full-parent review. If mainline differs from the recorded review base, the reviewed branch is delivered unchanged with `Review` plus `agent-rebase-needed` and the observed SHA is recorded for the human.
19. **Resolved — Already-satisfied outcomes:** initial children close after a verified empty diff; review follow-ups become stuck and force partial delivery; validation-repair children close only when the aggregate gate reruns green; and direct parents become parent-level stuck rather than delivering an empty branch.

## Testing Decisions

- Tests verify externally observable behavior — parsed outputs, GitHub command decisions, queue and label transitions, drain and delivery decisions, and stop reasons — not internal implementation details. The `run-backlog-v3.mts` and `run-prd-v4.mts` orchestrators stay integration-only and untested, consistent with the other `run-*` runners; all deterministic logic is tested at its module seam.
- Initial-decomposition output parsing is tested in its own module (prior art: `reviewer-result.mts`, `extra-review-parsers.mts`) against valid sub-task drafts, a no-work result, a needs-human result, missing tags, malformed JSON, and wrong shapes. Acquisition tests cover first-attempt success, second-attempt recovery for each retryable failure, diagnostic preservation, valid zero-draft fallback, and parent `agent-stuck` transition only after both attempts fail.
- Readiness-gate output parsing is tested in its own module (prior art: `reviewer-result.mts`) against each outcome — fixed, not-actionable, assumed — plus missing tags, malformed JSON, wrong shapes, and inconsistent states such as an outcome without its required complete body or evidence. Acquisition tests cover first-attempt success and second-attempt recovery; mutation tests cover success on attempts one through three, exact read-back verification, diagnostic preservation, and parent `agent-stuck` transition only after the applicable budget is exhausted.
- Readiness orchestration tests assert separate initial and follow-up batches, current accumulation grounding, sibling isolation to the active batch, exactly-once gating before coding, and identical outcome/failure handling for both child sources.
- Already-satisfied routing tests cover verified empty initial-child closure, rejection of a non-empty "already satisfied" branch, stuck review follow-up and partial delivery, validation-repair green/red reruns, and direct-parent `agent-stuck` without `Review`.
- Child-issue publication is tested at a pure command-builder and host-decision seam (prior art: `extra-review-issues.mts`) for the exact GitHub arguments, per-parent label creation/application, duplicate marker content, idempotent parent/child linking, verification ordering, created-but-unlinked recovery, and the close-on-integration command.
- Parent and child queue selection and label lifecycle are tested at a pure module seam (prior art: `extra-review-queue-state.mts`, `pickNextIssue`): resume selection requires all configured backlog labels plus `agent-in-progress` and precedes fresh selection; fresh eligibility requires all backlog labels and excludes in-progress/review/stuck; child selection uses the per-parent label; and claim, clean delivery, partial `Review` + `agent-partial` delivery, rebase-conflicted `Review` + `agent-rebase-needed` delivery, child-only `agent-stuck`, parent-level unrecoverable failure, exact idempotent label provisioning, terminal cleanup ordering, warning-only cleanup failure, and idempotent restart transitions are covered.
- The per-parent drain and partial-delivery decision is tested at the same queue-state seam: proceed while sub-tasks remain; enter partial-review mode after a stuck child when integrated work exists; exclude the original stuck child from review-start eligibility; mark an empty partial parent stuck; deliver reviewed partial work after a clean follow-up drain; and deliver reviewed partial work without another round if a review follow-up gets stuck.
- Sub-task integration tests cover reviewed-base mismatch, non-descendant child HEAD, successful fast-forward, push-before-close ordering, remote verification, and idempotent recovery after a crash before local update, after local update, after push, and after child close.
- Pre-review refresh tests cover unchanged mainline, advanced mainline, diagnostic checkpoint creation, successful rebase, force-with-lease replacement, original-fork provenance retention, refreshed review-base selection, and exclusion of unrelated mainline changes from full-parent review inputs. Conflict tests assert rebase abort, unchanged accumulation verification, no force push, diagnostic persistence, continued validation/review against the existing base, and no second automatic rebase.
- Terminal-mainline tests cover unchanged and advanced mainline, observed-SHA persistence, no second rebase or review, unchanged reviewed-head delivery, and exact `Review` versus `Review` + `agent-rebase-needed` transitions.
- Aggregate-validation tests cover green gates, exact repair-child evidence, one-child-per-gate budgets, readiness and engine routing, successful repair and rerun, inclusion of pre-review repair in full-parent review, no second full-parent round after pre-delivery repair, stuck repair, persistently red validation, and parent-level `agent-stuck` without review-ready labels on exhaustion.
- The decomposition fallback decision is tested as a pure branch: zero drafts route to direct parent work, while one or more drafts route every draft to child publication and readiness.
- Before extraction, characterization tests capture both `run-backlog-v3.mts` and `run-prd-v4.mts` round limits, recovery behavior, reviewer acquisition, no-progress detection, stuck classification, and terminal adapter effects. The extracted coder<->reviewer engine then tests the shared mechanism and runner-specific policies at its module seam, adding recovery coverage that does not currently exist outside the runners.
- Parent-context tests cover body precedence, comment author/timestamp rendering, newest-complete-comment retention under the byte cap, chronological rendering after selection, visible truncation notices, and identical normalized context across decomposition, readiness, direct-parent coding, and full-parent review.
- Parent-state tests cover first creation, idempotent update of the existing marked comment, schema rejection, missing or duplicate marker handling, transition timestamps, disagreement detection against branch/label/child state, restart reconstruction, and exclusion from normalized agent-facing comments.
- Host-mutation tests cover attempts one through three, exact read-back verification, preserved diagnostics and branch state on exhaustion, successful parent-level stuck fallback, and runner handoff when the terminal ownership/label transition also cannot be verified.
- Reuse of the bounded extra-review machinery is tested for the round budget of one: the single round runs, its follow-ups drain once, no second round runs, and expected post-drain budget exhaustion maps to clean parent delivery.
- Full-parent review acquisition tests cover first-attempt success, second-attempt recovery for every retryable result, `needs_human_review`, diagnostic preservation, no follow-up publication from invalid output, branch/artifact preservation, and parent-level `agent-stuck` only after the second attempt fails.
- Prompt contracts are checked with fixture outputs rather than by testing model quality; tests assert the host accepts only the expected tagged shapes for the initial decomposer and the readiness gate.
- Existing validation commands remain the primary behavior check before sub-task branches integrate and before the single extra review round runs.
- TUI tests assert the new agent and host stage names, parent-versus-sub-task ticket identity, phase transitions, working-log paths, and clean/partial terminal stop reasons without coupling loop control flow to emission success.

## Out of Scope

- Modifying `run-prd-v3.mts`, older PRD runners, or older backlog runners to call the shared engine is out of scope. Only `run-backlog-v3.mts` and `run-prd-v4.mts` adopt it.
- Parallel execution of sub-tasks or of readiness-gate runs is out of scope; the drain and the gate run sequentially in this implementation.
- More than one extra review round for a parent is out of scope.
- Auto-merging or auto-closing a parent issue is out of scope; delivery remains review-ready.
- Tracking sub-tasks as local markdown files or any store other than GitHub child issues is out of scope.
- Having the readiness gate mark sub-tasks stuck, or block the loop pending a human answer, is out of scope.
- A human approval step for generated sub-task or follow-up issues is out of scope.
- Cross-parent sub-task sharing or dependency linking between different parents' sub-tasks is out of scope.

## Further Notes

- The feature uses the glossary terms Issue-as-PRD loop, Parent issue, Parent state comment, Sub-task child issue, Initial issue decomposition, Issue accumulation branch, Partial delivery, Rebase-needed delivery, Sub-task readiness gate, Gate outcome, and Dropped sub-task, all recorded in `CONTEXT.md`.
- The design deliberately reuses existing gh-issue-backed publication, duplicate detection, queue-decision, and bounded extra-review patterns rather than building a parallel state store. The normal issue worker itself is not yet a reusable module; its deterministic coder<->reviewer mechanism is extracted behind the typed engine interface described above.
- The single highest-value structural change is extracting the shared coder<->reviewer engine and adapting `run-prd-v4.mts` without changing its behavior. It should be done first because direct-parent work, the sub-task drain, and the PRD-v4 issue loop depend on it.
- New agents (initial decomposer prompts and the readiness gate) need their own prompt files, mirroring the structure of the existing decomposer and reviewer prompts but with inputs and contracts specific to raw-issue decomposition and issue-draft review-with-fixup.
- The loop stays conservative: it prunes provably dead sub-tasks, resolves semantic ambiguities through recorded assumptions, stops a parent on exhausted technical failures, and quality-gates partial progress rather than discarding it when one sub-task cannot be landed.
